# 📄 Product Requirement Document (PRD) - V2

**Projeto:** Combustivel_APP (Flutter)
**Objetivo:** Migração de Persistência Local para Nuvem (`Supabase`) e Implementação de Exportação de Relatórios PDF Multiplataforma
**Status:** Atualizado / Pronto para Desenvolvimento

---

## 1. Resumo Executivo
O aplicativo **Combustivel_APP** realiza o controle de gastos veiculares. Este documento expande o escopo inicial de migração para o **Supabase** para incluir uma funcionalidade avançada de inteligência de negócios: a **Exportação de Relatórios em PDF**. O sistema deve permitir que o usuário filtre seus abastecimentos e gere um documento PDF consolidado e higienizado, com comportamentos nativos específicos para ambientes Windows (Desktop) e Mobile (Android/iOS).

## 3. Plano de Execução (Fases de Desenvolvimento)

### Fase 1: Setup de Infraestrutura e Dependências
1. Inserir os pacotes no `pubspec.yaml`:
   - `supabase_flutter` (Persistência em Nuvem)
   - `pdf` (Geração do documento PDF)
   - `open_file` (Abertura de arquivos no Desktop/Windows)
   - `share_plus` (Compartilhamento nativo no Mobile)
2. Configurar o `Supabase.initialize()` no `main.dart`.

### Fase 2: Camada de Repositório (Data Layer)
1. Construir `SupabaseRepository` para operações CRUD de `Veiculo` e `Abastecimento`.
2. Garantir tratamento de tipagem via `num.toDouble()` para evitar quebras de runtime.

### Fase 3: Refatoração da Camada de Apresentação (UI/State)
1. Substituir a leitura do `shared_preferences` pelas chamadas reativas do `SupabaseRepository`.
2. Adicionar feedbacks de carregamento (`CircularProgressIndicator`) nas views de listagem.

### Fase 4: Exportação de Dados Filtrados para PDF (Nova)
Esta fase detalha a implementação do motor de relatórios respeitando as restrições arquiteturais multi-plataforma da aplicação.

#### 4.1. Regras de Negócio do Relatório
* **Escopo do Conteúdo:** O PDF deve conter exclusivamente os registros resultantes do filtro atualmente ativo na tela de listagem (ex: filtrado por veículo, período ou tipo de combustível).
* **Formatação:** O layout deve ser estruturado em formato de tabela organizada contendo: Data, Veículo, Posto, Litros, Preço/Litro e Valor Total. Uma seção de rodapé deve exibir o somatório do Valor Total e a Média de Consumo Geral do período filtrado.

#### 4.2. Especificações por Plataforma

```
                        [ Ação da View: Exportar ]
                                     |
                                     v
                        [ Camada de Serviço: MVCS ]
                              (PdfService)
                       Gera PDF estruturado em memória
                                     |
                +--------------------+--------------------+
                |                                         |
                v                                         v
       [ Se Windows (Desktop) ]                     [ Se Mobile ]
                |                                         |
   Salva em arquivo temporário              Abre menu nativo do sistema
  Invocado via pacote: `open_file`           Via: `Share.shareXFiles`
                |                                         |
                v                                         v
Abertura automática no leitor padrão        WhatsApp, Google Drive, etc.
```

* **Comportamento Windows (Desktop):**
  * O aplicativo deve gerar o PDF em memória, salvá-lo em um diretório temporário do sistema operacional e disparar a visualização imediata.
  * **Diretriz Técnica:** Utilizar o pacote `open_file` para invocar automaticamente o visualizador padrão do Windows (Adobe Reader, Microsoft Edge, etc.) assim que o arquivo for consolidado, garantindo fluidez profissional.
* **Comportamento Celular (Android/iOS):**
  * O aplicativo deve gerar o PDF e acionar a folha de compartilhamento nativa do sistema operacional (Share Sheet).
  * **Diretriz Técnica:** Utilizar o método `Share.shareXFiles`. Ele provê a experiência padrão de mercado onde o usuário decide se deseja enviar o documento por WhatsApp, salvar no Google Drive/iCloud ou realizar o download interno.

#### 4.3. Arquitetura e Lógica de Serviço (Padrão MVCS)
* **Isolamento de Escopo:** Toda a lógica de montagem estrutural, estilização e cálculo dos dados do PDF deve residir estritamente no `PdfService` (Camada de Serviço/Utility).
* **Abstração da View:** A interface gráfica (**View**) não deve possuir conhecimento de "como" o PDF é renderizado. A View deve unicamente disparar a lista filtrada de objetos para o serviço.
* **Consumo de Recursos:** Os dados devem ser processados uma única vez. O `PdfService` fará a interceptação da plataforma (`kIsWeb`, `Platform.isWindows`, etc.) apenas no estágio final para determinar a estratégia de saída/entrega do arquivo (memória temporária ou buffer de stream para compartilhamento).

---

## 4. Requisitos Não Funcionais Técnicos
* **Performance de Processamento:** A geração do PDF deve rodar de forma assíncrona para não travar a Main Thread (UI) da aplicação, exibindo um indicador de progresso para o usuário durante a compilação do relatório.
* **Gerenciamento de Arquivos:** No Windows, os arquivos temporários gerados na pasta de cache devem utilizar uma convenção de nomenclatura única (ex: `relatorio_abastecimento_${DateTime.now().millisecondsSinceEpoch}.pdf`) para evitar colisões e travamentos de escrita.
